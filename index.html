Values

Four things I hold myself to, in this order.

  1. 01

    Deliver the solution

    Working outcomes, not just code. A change is done when it is verified through the path real users take — the end-to-end spec, the seeded boot test, a live browser — and the guide and team memory are updated in the same commit.

  2. 02

    Security

    Secure by construction: OIDC at the front door, tenant isolation that fails closed and is enforced again by the database, protected fields encrypted, and a shift-left pipeline every service inherits — SAST, SCA, secrets, IaC, signed images.

  3. 03

    Compliance

    Regulation is an input, not an afterthought. Statutory thresholds are versioned with a review date, compliance annotations cite the clause, financial audit trails are hash-chained and PHI access is logged — so an audit is a report, not a scramble.

  4. 04

    Future-proof

    Built to survive replay, retry and the next service extraction: outbox events, idempotent consumers, absolute values on the wire, one database and migration chain per service, and architecture rules that fail the build when someone forgets.

Principles

Rules I work by. Each one was paid for.

Distilled from the engineering standard I help maintain and grouped under the four values. None of them came from a book — every one is a defect that happened, written down so it can't happen twice.

  1. A read model isn't built until something writes it.

    Producer, consumer, backfill, and one row actually observed. Three of four is a table full of blanks that compiles perfectly.

  2. No form is done without an end-to-end spec.

    Happy path, empty submit blocked, bad phone, bad email, inverted date range, tampered POST → 400, cross-tenant id → 404. Linted statically, proven at runtime.

  3. Verify through the path the code uses.

    A database shell is a different principal and tenant scope than the running service; a boot test with seeders off proves beans assemble, not that the service works. Make the test report what it sees.

  4. Tenant isolation fails closed.

    No ambient tenant, no default tenant. A request without a tenant header is a 400; a consumer without a tenant record header drops the message. Row-level security at the database is the last line, not the only one.

  5. Not found, never forbidden.

    A by-id load under the wrong tenant answers 404. A 403 confirms the row exists — and that is already a leak.

  6. A convention becomes a rule in the same change.

    If a review finds a secure-coding mistake, the fix ships with the Semgrep or ArchUnit rule that would have caught it. Otherwise the review is a wish.

  7. Soft-delete only. Ghost rows leak.

    Every tenant table carries deleted_at; every collection carries the filter. A hard delete destroys the audit trail, a missing filter resurrects the dead.

  8. Thresholds are versioned, never hard-coded.

    Any amount, percentage or day-count a regulator can change lives in a versioned service with a review date. Annotations cite the clause, so a stale rule surfaces on a dashboard instead of in an audit.

  9. Protected data is tagged, encrypted and logged.

    PII and PHI fields carry a category annotation, sit behind a field-level encryption converter, and every read of health data lands in an access log. Never in a URL, never in a log line.

  10. Idempotent by constraint, absolute on the wire.

    Insert the dedupe marker on the producer's key, in the same transaction, before the handler runs, and let the unique constraint reject the replay. Carry the new balance, not the delta — a replay from the beginning is legitimate.

  11. Side effects go through the outbox.

    Never a cross-module service call, never @Async — it loses the tenant context and has no retry. Write the event in the same transaction as the fact; a relay delivers it.

  12. Every round trip costs fifty milliseconds.

    Users are far from the data centre. No cross-service HTTP inside a transaction, page chrome cached per tenant and user, no N+1 — and a hot-path change states before/after numbers, or it isn't a result.

Working with agents

Coding agents are fast, forgetful colleagues. I design for that.

I use Claude Code across a 700k-line codebase every day. What makes it work isn't the prompt — it's the engineering around it.

01

The contract lives in the repo

A rules file is the first thing any agent reads: entity and tenancy rules, the service standard, the form gate, the AppSec regime, the performance budget. Twenty-two rules, each traceable to a defect that actually happened. Humans and agents are held to the same text.

02

Memory is tiered and kept current

Base knowledge, then per-domain group memory, then platform. Updating a module's memory ships in the same change as the behaviour — stale knowledge is a defect, same as a stale comment. Over 160 memory files, indexed.

03

Tokens are a budget

I wrote skills that compress agent prose without losing technical substance, push for the smallest correct diff, and fan audits out to read-only subagents so only findings return to the main context. Logs are filtered before anything reads them.

04

Verification over trust

Agents claim; the build, the Playwright suite and a live browser verify. An agent-found convention becomes a Semgrep rule in the same change. Migration numbering, cross-tenant loads and form standards are checked by scripts, not by reading.
